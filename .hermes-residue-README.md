# Item-residue re-render (batches 01-10) — state and how to finish it

What this is: the batch-08 work proved the pipeline end to end (audit -> prompt fix -> re-render ->
verify -> apply, with backups). This directory is the same pipeline turned on the REST of the audit:
266 unique flagged item tiles from `item_audit_findings/batch-0*.json`, of which 13 were already
re-rendered and verified (batch 08), leaving 253.

## What changed in the product first (committed 79464b1)

The audit residues showed the same two failures the batch-08 findings had, at shelf scale:

1. Item prompts were handing the model a **category-and-rarity line** or **prose addressed to a reader**
   in place of an object description ("Wondrous item, legendary This item first appears to be a Large
   sealed iron barrel…" -> a live giant crab; "You can use an action…" -> a person holding the thing).
   Both are now recognised and dropped (`snippet_is_type_line`, `snippet_is_second_person`).
2. Most named objects had **no shape cue at all**, so the model free-filled from the noun (an "Arrow"
   as brass cartridges, a "Bell" as a cathedral bell on a wheeled yoke, a "Lamp" as an electric table
   lamp). ITEM_CUES went from 34 to 96 entries, each stating only what the record already says.
3. `construct_cue` no longer fires on a token or charm (a Swan Boat Feather Token is not a boat), and
   `KINDS["item"]` is 768x1024 like the other kinds (the hosted path could still emit a square tile
   into a 2:3 shelf).

Effect measured on the flagged records themselves: **182 of 266** flagged tiles now produce a
DIFFERENT prompt than the one the auditor judged (cue added, or misleading snippet dropped). Those are
the tiles in this run. The remaining 84 have a cue already and the art still came out wrong, so they
need something other than a prompt rewrite - see "What the residue still needs" below.

## The run

    gen_residue.py     renders each target through the app's own prompt builder and comfy graph
                       (832x1216, the shelf's bucket), one candidate per tile into residue_cand/
    residue_ledger.jsonl   one line per attempt: index, name, class, seed, candidate, backup, sha_before,
                       the exact prompt used, error. The generator SKIPS anything already in the
                       ledger, so restarting costs nothing.
    residue_redo_backup/item/   the live tile copied, sha256-recorded, before anything is written
    apply_residue.py   applies reviewed winners (winners.json = {index: seed}) through the app's own
                       save(); refuses a tile whose backup is missing or no longer matches, and records
                       the applied result (dims, sha before/after, re-encode diff) into residue_applied.json

Throughput is ~2 minutes per tile on the LAN ComfyUI box, so the 182-tile pass is about 5-6 hours.

**It is kept alive by a cron watchdog** (job `3138c5f0f498`, every 30m, no agent, silent unless it
restarts something or the run completes): `~/.hermes/work/item_redo_watchdog.py` decides from the
ledger and the log whether the generator is alive, stalled (no write for 45m) or finished, and
restarts it detached if needed. Check it by hand any time:

    python3 ~/.hermes/work/item_redo_watchdog.py --dry-run     # targets / generated / live pids
    tail -3 gen_residue.log

## Reviewing and applying what it produces

Nothing is applied automatically: every candidate is reviewed against the issue the auditor recorded
before it replaces the live tile. `residue_verify_manifest.json` lists what is waiting (index, name,
class, the recorded issue, candidate path, current live path, the prompt used). Judge each candidate
against its own issue, then:

    echo '{"7": 11, "9": 11}' > winners.json
    .venv/bin/python apply_residue.py winners.json --dry-run   # then without --dry-run

## What the residue still needs (measured, not guessed)

The 84 tiles whose positive prompt did NOT change are the hard ones: the model follows the noun's
prior and reads a "no X" clause inside the POSITIVE prompt as a mention of X. Measured examples:

  * "Ring Mail" - cue says "a mail coat of thousands of interlocking silver rings, no plate, not a
    finger ring"; the art is a polished plate harness with gold trim.
  * "+1 Mithral Chain Shirt" - cue says "a sleeveless tunic of thousands of interlocking iron rings";
    the art is a navy cloth shirt hung with gold chains.

**That lever is now implemented** (commit `a91d3b8`): `ITEM_NEGATIVES` (24 families) +
`item_negative()` append the wrong reading each family has produced to the standard item bans - plate
armour and jewellery rings for mail, bulbs and power cords for lamps and lanterns, brass cartridges
for ammunition, motor trucks for vehicles, face and wearer for helmets. Items previously passed
`negative=None`, so this is the first time the item shelf gets anything beyond the standard bans.
The run is two-phase for that reason: REST=0 renders the tiles whose positive prompt changed,
REST=1 then renders the rest under the new negatives. The watchdog picks the phase from the work
left (see `restart()`), so it walks from one to the other without being told.

A second group cannot be fixed by any prompt: records whose subject is not an object at all
("Standard of Living: Poor (per day)", "Hot Bath", "Feed (per day)", "Unarmed strike", "Weakness",
"Ill-luck"). Those describe a service, a state or an action. They need a product decision (a scene
frame with no people? a rulebook-style illustration? or drop them from the shelf), not a shape cue.

## Rules learned in the verification rounds (each one cost a re-render)

1. **A ban inside a positive prompt is a mention, not a ban.** The ammunition cue read "a bundle of
   short fletched shafts with small iron points, `no brass cartridges, no bullets`" and every draw
   came back as brass cartridges; "Bit and bridle"'s cue ended "`no horse, no rider`" and the draw was
   a live horse; "Hide Armor" and "Padded Armor" both said "`no wearer`" and both came back worn by a
   body. All 36 such clauses are gone from ITEM_CUES (commit `9136453`); the readings are named in
   ITEM_NEGATIVES instead. **Cue = what it is. Negative = what it must not be.**
2. **Both tables are first-match-wins**, so a specific family entry must sit ABOVE a general one
   (the belt and plate entries are at the head of ITEM_NEGATIVES, or the garment/armour ban wins the
   lookup and the tile loses the ban it needed).
3. **The two tables share pattern text**, so a replace anchored on a regex line can land in the wrong
   table - verify a negative by calling `item_negative(name)`, not by grepping the file.
4. **Never put a negation in a cue**, not even in a new one: `"an empty suit of riveted steel plate
   armour, no wearer"` was written and removed in the same session for exactly that reason.
5. **When the prompt changes, re-render - do not review the old candidate.** A candidate drawn under
   superseded text is not evidence about the current pipeline; reviewing it wastes a reviewer and
   risks applying art the current code would not produce.
6. **A name that is a filing label is part of the prompt's problem**: "Ammunition, +1" drew modern
   ammunition whatever the cue said, so the prompt name is rewritten (`_NAME_OVERRIDES`) to the noun
   the record means ("Arrows, +1"). The database name is never touched.
7. **An in-place table rewrite re-wraps lines, and a later multi-line find/replace then matches
   loosely** - one such edit swallowed the rest of `ref_portraits.py` into the ITEM_CUES tuple.
   Compile after every edit (`py_compile`), and prefer exact single-line replacements.

8. **The prompt NAME is the dominant variable, not the cue.** Where a cue and a family ban are both
   correct and the tile still comes back wrong, the record's own noun is winning: "Ammunition, +1"
   draws cartridges, "Sling bullet" draws rifle bullets, "Eyes of the Eagle" draws a live eagle,
   "Hide Armor" draws plate with a wearer, "Potion of Animal Friendship" puts animals in the bottle.
   `_NAME_OVERRIDES` handles exact names and `_NAME_PATTERNS` handles a family (every
   "Ammunition (range ...)" record prompts as Arrows, parenthetical kept). The database name is never
   touched. Reach for this FIRST on a second failure, not a fourth seed.
9. **A ban can bite the object itself.** The warhammer family banned "head" - so the model drew a
   spiked skull-faced HELMET instead of a weapon. Ban the wrong reading (helmet, skull, armour), never
   a word the right object needs.
10. **State the presentation instead of banning the subject.** "Laid out flat on a plain surface" or
    "hanging on a plain peg" fixed the figure class where bans did not: a flat-laid bridle cannot be on
    a horse, a flat-laid suit cannot be worn, and the phrasing is positive so nothing is summoned.
11. **Style is a separate acceptance axis, and "studio" words work against it.** SDXL Turbo at CFG 2.0
    will not take a strong negative, and raising CFG to 4.5 fixes the object while turning the tile
    into a glossy hero shot on a dark vignetted wall. The shelf look comes from shelf language -
    "isolated on a plain blank grey background in soft even painted light" - and a tile that fixes the
    object but changes the look is NOT applied. Judge style against two untouched library tiles.
