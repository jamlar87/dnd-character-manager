# D&D Character Manager Comprehensive Audit Remediation Plan

> **For Hermes:** Implement in vertical slices. Run tests after every slice and commit each milestone.

**Goal:** Harden the application, protect character data, improve database reliability, expand regression coverage, and gradually reduce monolithic coupling without changing D&D behavior.

**Architecture:** First secure the existing application in place. Then add explicit migrations and authorization tests. After behavior is protected, extract database/auth/data/progression services behind compatibility wrappers. Finally split templates and route modules incrementally.

**Tech Stack:** FastAPI, SQLite, Jinja2, pytest, bcrypt, ReportLab.

---

## Milestone 1 — Security gate

- Remove automatic `admin/admin` seeding.
- Require a non-default `SECRET_KEY` outside test/development mode.
- Add server-enforced session expiry and cleanup.
- Disable the current unauthenticated password reset; add authenticated password change.
- Add same-origin validation for unsafe browser requests.
- Add security response headers.
- Return generic API errors with request IDs; keep exception details in logs.
- Add tests for all behaviors before implementation changes.

## Milestone 2 — Database reliability

- Add indexes for campaigns, encounters, NPCs, traps, and relationships.
- Replace silent schema drift with versioned migrations and schema validation.
- Preserve compatibility with existing databases during migration.
- Add migration tests against fresh and legacy schemas.

## Milestone 3 — Authorization and progression coverage

- Test cross-user read/update/delete behavior for every owned resource.
- Add character creation, multiclass level-up/de-level, HP, spell slots, feature, and PDF characterization tests.
- Add malformed-state and repeated-transition tests.

## Milestone 4 — Safe structural extraction

- Extract `db.py` and `auth_service.py`, retaining compatibility imports.
- Extract data loaders and progression services.
- Split `routes/characters/all.py` by domain only after tests pass.
- Split `sheet.html` into partials and move CSS/JS to static assets.
- Centralize web/PDF data enrichment.

## Milestone 5 — Operations and performance

- Make campaign-expert path configurable.
- Cache immutable JSON loads by path and mtime.
- Lazy-load DM-only datasets.
- Add startup-loader timings and CI checks.
- Add PDF output tests and remove duplicate spell loading.
- Add backup/restore and clean-environment verification.

## Verification gate

```bash
.venv/bin/python3 -m pytest -q
.venv/bin/python3 -m compileall -q main.py data.py routes pdf_generator.py
```

No milestone is complete with failing tests, unreviewed security findings, or unverified database behavior.

## Current implementation order

1. Security tests and security implementation.
2. Migration/index tests and implementation.
3. Authorization/progression tests.
4. Service extraction in small compatibility-preserving slices.
5. Template/PDF/operations work.
6. Full verification and independent review.

The four deleted root audit scripts are unrelated to runtime behavior and should be restored or deliberately removed in a separate cleanup commit after confirming they are obsolete.

---

## Acceptance criteria

- No unauthenticated password reset.
- No default admin credential creation.
- Expired sessions are rejected.
- Unsafe cross-origin browser requests are rejected.
- API 500 responses contain no exception text.
- Security headers are present.
- All owned-resource queries have supporting indexes.
- Existing test suite and new regression suites pass.
- Character progression behavior remains unchanged except for corrected security/data-integrity behavior.
- Each structural extraction has tests proving compatibility.
- Final report names any remaining work instead of claiming incomplete refactors are finished.

## Rollback

Each milestone is isolated in a commit. Restore the previous commit if a migration or compatibility wrapper fails. Never edit the live database manually without a backup and a tested rollback path.

## Data safety

Before applying migrations to the live database:

```bash
cp data/characters.db data/characters.db.pre-remediation.$(date +%Y%m%d%H%M%S)
```

Never commit the database, logs, secrets, or PDF manuals.

---

## Review requirement

Before each milestone is treated as complete, inspect the diff, run the full test suite, run a security scan, and review database query plans for affected queries.

The plan deliberately separates security and behavior changes from refactoring so regressions can be isolated.

## End state

The desired end state is a thin FastAPI bootstrap, explicit services and repositories, canonical data registries, versioned migrations, route-level authorization tests, componentized templates, and a PDF renderer consuming the same prepared character data as the web sheet.

This document is the source of truth for the remediation sequence.

## Detailed task slices

### Security

1. Write tests for default-admin absence and secret validation.
2. Write tests for expired sessions.
3. Write tests for safe error responses and request IDs.
4. Write tests for same-origin enforcement and security headers.
5. Write tests for authenticated password change and disabled reset.
6. Implement each slice and run its focused test.

### Database

1. Write query-plan tests for every owner/foreign-key query.
2. Add indexes.
3. Add migration version tracking.
4. Add schema validation.
5. Test fresh and legacy databases.

### Progression

1. Character creation state assertions.
2. Single-class level transitions.
3. Multiclass level transitions.
4. De-level ownership and ASI tests.
5. Spell slots and expanded list tests.
6. Repeated transitions and malformed state tests.

### Refactoring

Extract one module at a time, keep imports compatible, run tests before and after, then remove duplicate implementation only after callers move.

### Operations

Add configurable paths, clean install/compile checks, startup timings, PDF smoke checks, and documented backup/restore commands.

## Appendix: security invariants

- A password reset request alone never changes a password.
- A token is single-use and expires.
- A session older than its expiry is invalid.
- A cross-origin unsafe request without same-origin proof is rejected.
- API clients never receive exception internals.
- The server never creates a known default administrator.

---

## Appendix: database invariants

- Every resource query scopes by owner or an explicit share policy.
- Every foreign-key collection query has an index.
- Migration errors are visible and actionable.
- Existing user data survives schema upgrades.

---

## Appendix: test invariants

- New behavior has a failing test before implementation.
- Tests assert data and authorization outcomes, not only HTTP status.
- Full suite runs after every milestone.

---

## Appendix: refactor invariants

- No behavior changes hidden inside extraction commits.
- Compatibility imports remain until all callers move.
- Data precedence is explicit.
- Web and PDF renderers use the same prepared data contract.
